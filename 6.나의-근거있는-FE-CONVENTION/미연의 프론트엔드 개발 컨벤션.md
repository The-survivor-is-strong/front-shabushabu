### 1. 폴더 구조

<b> 🎯 목표 </b>

**재사용성과 응집성의 균형**을 통해 유지보수성과 확장성을 동시에 확보하기

- 컴포넌트 재사용과 코드 분리가 핵심이지만 과도한 추상화는 오히려 복잡성을 증가시킴
- 따라서 **실용적이고 직관적인 구조**를 통해 개발 생산성을 극대화하는 것이 목표

<b> 🧩 각 폴더의 역할과 기준 </b>

**1. `components/@atom/`**

**기준**: 디자인 시스템 레벨의 최소 단위 컴포넌트

**특징**:
- 프로젝트 전반에서 일관된 디자인을 위한 기본 빌딩 블록
- 비즈니스 로직 없음, 순수 UI만 담당
- props를 통해서만 동작하는 순수 함수형 컴포넌트

**@atom 네이밍의 근거**:
- 알파벳 순서로 최상단에 위치 (가장 기본이 되는 컴포넌트들)
- 특수문자로 시각적 구분 효과
- Atomic Design 철학 반영

**2. `components/domain/`**

**기준**: 특정 도메인 관련 컴포넌트 (2회 이상 재사용, 정말로  `formal` 한지)

**특징**:
- 해당 도메인의 비즈니스 로직 포함
- 여러 화면에서 재사용 가능
- 도메인 특화 상태와 로직 캡슐화

**근거**: 도메인 지식을 캡슐화하여 비즈니스 로직의 재사용성을 높이고, 도메인별 변경사항의 영향 범위를 제한

**3. `components/[screen]/`**

**기준**: 특정 화면에서만 사용되는 조합형 컴포넌트

**특징**:
- domain 컴포넌트들을 특정 화면에 맞게 조합
- 화면별 특화 로직 포함
- 해당 화면의 요구사항에 최적화

**근거**: 화면별 특화 요구사항을 만족하면서도, 페이지 컴포넌트의 복잡도를 줄이기

**4. `pages/`**

**기준**: 라우팅과 페이지 레벨 상태관리만 담당

**특징**:
- 컴포넌트 조합 및 데이터 흐름 제어
- 실제 UI 로직은 최소화
- 라우팅 파라미터 처리 및 전역 상태 연결

**근거**: 페이지는 컴포넌트 조합의 역할에 집중하여 복잡한 UI 로직을 하위 컴포넌트로 위임

**🚀 이 구조의 장점**

**1. 명확한 책임 분리**
각 폴더의 역할이 명확하여 새로운 컴포넌트를 어디에 둘지 고민하는 시간이 단축

**2. 점진적 복잡도**
`@atom` → `common등 중간(유동적인 부분)` → `domain` → `screen` 순으로 복잡도가 증가하여 학습 곡선이 완만

**3. 재사용성 최적화**
필요에 따라 컴포넌트를 적절한 레벨에 배치하여 과도한 추상화를 방지

**4. 유지보수성**
변경 사항의 영향 범위를 예측할 수 있어 안전한 리팩토링이 가능

**5. 확장성**
새로운 도메인이나 화면 추가 시 일관된 구조를 유지

**🔄 점진적 적용 방법**

1. **@atom 컴포넌트 먼저 정의**: 디자인 시스템 구축
2. **common 컴포넌트 식별**: 반복되는 UI 패턴 추출
3. **domain 컴포넌트 분리**: 비즈니스 로직 캡슐화
4. **screen 컴포넌트 생성**: 화면별 특화 로직 분리
5. **pages 단순화**: 조합 로직만 남기기
